## 1. 核心定义与设计思辨 (Core Definition & Speculation)

### 1.1 绝对坐标的“刻舟求剑”陷阱
传统的移动端脚本（如 Appium 录制）通常记录绝对坐标 `(x=500, y=1000)`。这种方式在工程落地中极其脆弱：
*   **分辨率碎片化**：在 iPhone 14 Pro 上录制的脚本，在 iPhone SE 上点击位置会偏移到“虚空”。
*   **响应式布局（Responsive Layout）**：现代 App 会根据屏幕宽度自动调整按钮间距。宽屏手机上的“提交”按钮可能比窄屏手机更靠右。

### 1.2 “橡皮膜”理论 (The Rubber Sheet Theory)
AceAgent-Swarm 将 UI 视为一张印有图案的**橡皮膜**。
*   当手机屏幕变大或拉长时，这张橡皮膜被拉伸了。
*   虽然图案（按钮）的绝对位置变了，但图案与图案之间的**相对几何关系**（拓扑）是恒定不变的。
*   **动作面引擎的核心任务**：利用上一篇文档找到的“核心锚点星群”作为图钉，计算出这张橡皮膜当前的**拉伸张力（变换矩阵）**，从而推导出目标按钮现在被“拉”到了哪里。

## 2. 宏观机制：全局弹性坐标系 (Global Elastic Coordinate System)

该机制适用于页面中相对固定的元素（如：底部 Tab 栏、顶部功能键、悬浮窗 FAB）。

### 2.1 离线：相对归一化记录
在“离线进化/录制”阶段，我们不记录点击点的像素值 $(x, y)$，而是记录它在**核心锚点多边形**中的相对位置。

*   **输入**：
    *   核心锚点 $C_1$ (左上返回键) 坐标
    *   核心锚点 $C_2$ (右下“我的”Tab) 坐标
    *   目标点击点 $T$ (中间的“去支付”按钮)
*   **计算机制**：
    系统构建一个以 $C_1$ 为原点，$C_1 \to C_2$ 为主轴的虚拟坐标系。记录 $T$ 在该坐标系下的**比例系数 (Ratio Coefficients)**，而非距离。
    *   *直观理解*：记录“目标按钮位于从 $C_1$ 到 $C_2$ 连线的 50% 处，且垂直向下偏移 20% 的位置”。

### 2.2 在线：动态仿射投射 (Dynamic Affine Projection)
当 Agent 在一台陌生的新手机上运行时：

1.  **锚点锁定**：状态面引擎通过 OCR/CV 找到了当前屏幕上的 $C_1'$ 和 $C_2'$。
2.  **张力计算**：
    系统对比新旧锚点的距离，发现：
    *   水平方向拉伸了 1.2 倍（屏幕变宽了）。
    *   垂直方向拉伸了 1.1 倍（屏幕变长了）。
3.  **坐标还原**：
    应用上述拉伸倍率，将离线记录的比例系数映射回当前屏幕的绝对坐标 $T'$。
    $$T' = Matrix_{stretch} \times T_{ratio} + Offset_{origin}$$

**效果**：无论是在折叠屏展开态，还是在带刘海的小屏手机上，点击指令都能像“吸铁石”一样，精准吸附在目标按钮的几何中心。

## 3. 微观机制：局部伴生锚点 (Local Micro-Anchors)

该机制适用于动态列表、Feed 流等**位置不固定**的元素（如：点击列表中的某一行、点击特定评论的点赞）。

### 3.1 痛点：列表项的“幽灵漂移”
在长列表中，目标元素（如“订单 #1001”）的位置取决于滚动条，全局锚点（顶部/底部）无法决定它在哪。此时全局弹性坐标系失效。

### 3.2 解决方案：伴生绑定 (Satellite Binding)
动作面引擎引入**“伴生锚点”**概念。动作不再绑定页面，而是绑定具体的**内容特征**。

*   **离线定义**：
    *   **意图**：`CLICK_ORDER_ITEM`
    *   **伴生特征**：OCR 文本 "订单 #1001" 或 特定 Icon 图案。
    *   **相对偏移**：点击位置位于该文本 **"右侧 100px"** 或 **"中心"**。
    
*   **在线执行流程**：
    1.  **局部扫描**：在当前屏幕的**中间动态区（Middle Zone）**进行 OCR 扫描。
    2.  **特征锁定**：找到文本 "订单 #1001" 的 Bounding Box。
    3.  **偏移执行**：直接以该 Bounding Box 为基准，施加相对偏移量，生成点击坐标。

**效果**：即使列表顺序变了（从第3行变成了第5行），或者字体调大了，Agent 依然能紧紧咬住目标文字旁边的操作按钮。

## 4. 宏动作机制：感知-行动循环 (Perception-Action Loop)

针对“目标不在当前屏幕内”的常见场景，动作面引擎内置了**原子级规划能力**，无需调用云端大模型。

### 4.1 "Swipe-to-Find" (滑动寻找)
这是一个封装好的**状态机宏动作**：

*   **Step 1 (Check)**：在当前屏幕寻找目标（全局映射 或 局部伴生）。
*   **Step 2 (Decision)**：
    *   如果找到 -> 执行 `Tap`，任务结束。
    *   如果没找到 -> 进入 Step 3。
*   **Step 3 (Act)**：执行标准 `Swipe Up` (上滑) 动作，幅度为屏幕高度的 60%（预留重叠区防止漏看）。
*   **Step 4 (Verify)**：
    *   检查屏幕是否到底（通过像素是否不再变化判断）。
    *   如果未到底 -> 回到 Step 1。
    *   如果已到底仍未找到 -> 抛出 `TargetNotFound` 异常，请求 System 2 (大模型) 介入。

**优势**：这一过程完全在端侧闭环，延迟极低（< 200ms/帧），模拟了人类“快速刷屏找入口”的肌肉记忆。

## 5. 安全护栏：最后一英里校验 (Last-Mile Safety Check)

为了防止 AI“手滑”导致不可逆的后果（如误删数据、误转账），动作面引擎在发出 `adb tap` 指令前的**最后 10 毫秒**，会执行一次安全断言。

### 5.1 语义红线检测 (Semantic Red-line)
在计算出点击坐标 $(x, y)$ 后，系统会反查该坐标下方的 UI 元素内容。

*   **检测逻辑**：
    *   读取点击区域 $\pm 50px$ 范围内的文本。
    *   与**“高危词库”**（如：删除、注销、Pay、Transfer）比对。
*   **阻断机制**：
    *   如果当前意图是 `VIEW_DETAILS`（查看详情），但点击位置检测到了 "Delete"（删除）。
    *   **动作引擎强制中断**，抛出 `SafetyIntervention` 异常。
    *   这有效防止了因为 UI 突然弹窗导致的点错位置。

### 5.2 视觉反馈闭环 (Visual Feedback Loop)
执行点击后，引擎不会立刻认为成功，而是会等待 300-500ms，再次截取关键帧与**“预期后置状态”**比对。
*   **预期**：点击“搜索”后，键盘应该弹起，或出现加载转圈。
*   **实际**：画面完全静止。
*   **结论**：点击无效（可能按在了透明层上）。系统自动触发**“微扰重试”**（位置随机偏移 5px 再点一次）或报错。

## 6. 总结 (Summary)

AceAgent-Swarm 的动作面引擎彻底抛弃了死板的脚本式点击。

它像一个**高适应性的驾驶员**：
1.  **全局弹性**：不管车（手机）变宽还是变窄，它知道方向盘（核心功能键）的相对位置。
2.  **局部伴生**：不管路标（列表项）移到了哪里，它眼睛盯着路标操作。
3.  **自主寻找**：看不见路标时，它知道往前开（滑动）去找，而不是原地熄火。
4.  **安全本能**：在踩油门前，它会下意识确认脚下是不是刹车（高危检测）。

这种机制确保了 Agent 的操作具备了**工业级的鲁棒性**，是实现大规模无人值守自动化的基石。
