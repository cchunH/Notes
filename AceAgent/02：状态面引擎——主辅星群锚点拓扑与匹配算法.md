## 1. 核心定义与设计思辨 (Core Definition & Speculation)

### 1.1 为什么放弃“全图特征”？
在传统的 CV（计算机视觉）任务中，识别一张图片通常依赖 ResNet 或 CLIP 提取全局 Feature Map。但在移动端 UI 自动化的语境下，这种方法存在致命的**“信噪比倒置”**问题：
*   **现象**：一个电商 App 的首页，90% 的像素（Banner 图、商品流、直播窗口）是动态且高频变化的，只有 10% 的像素（顶栏、底栏、功能入口）是静态的。
*   **推论**：若对全屏进行 Embedding，动态噪音的权重将淹没静态信号。两张截然不同的“首页”（昨天 vs 今天）在向量空间距离极远，而一张“首页”和一张“商品详情页”（如果都卖同一个商品）反而在向量空间距离极近。
*   **决策**：必须放弃“全图感知”，转向**“稀疏特征拓扑（Sparse Feature Topology）”**。

### 1.2 星群拓扑哲学 (Constellation Philosophy)
我们将 UI 页面视为夜空。我们不记忆“夜空的颜色”（因为会有云雾/动态内容），我们只记忆**“恒星的相对位置”**（即锚点）。
只要猎户座腰带上的三颗星相对位置不变，无论背景是否有云（广告弹窗）、无论是在北半球还是南半球观测（分辨率拉伸），我们都能确认这是猎户座。

**“状态面”的数学定义**：
状态 $S$ 不是像素集合，而是一个由 $N$ 个特征点构成的有向图 $G(V, E)$，其中 $V$ 是锚点集合，$E$ 是锚点间的几何约束关系。

## 2. 锚点数据结构与异构归一化 (Data Structure)

为了兼容 OCR（文本）和 CV（图标），我们需要一个**异构归一化**的数据结构。

### 2.1 数据模型
```typescript
interface AnchorNode {
  // 唯一标识符
  id: string; // e.g., "core_01_back_btn"
  
  // 类型定义：决定了匹配算法
  type: 'TEXT' | 'ICON' | 'SHAPE';
  
  // 内容指纹：异构的核心
  payload: {
    text?: string;        // OCR 文本内容，如 "设置"
    icon_hash?: string;   // pHash 或 SIFT 特征描述子
    color_hist?: number[];// 局部颜色直方图 (辅助校验)
  };

  // 归一化坐标 (0.0 - 1.0)
  norm_bbox: { x: number, y: number, w: number, h: number };

  // 角色定义
  role: 'CORE' | 'AUXILIARY'; 
  
  // 固有稳定性评分 (0-100)
  stability_score: number;
}
```

### 2.2 异构处理策略
*   **文本 (Text)**：优先级最高。抗干扰性最强，不受 Dark Mode（黑白反转）影响。匹配时采用 Levenshtein Distance（编辑距离）容错（如 "账号" vs "帐号"）。
*   **图标 (Icon)**：用于无文本场景（如“返回箭头”、“汉堡菜单”）。
    *   *技术难点*：图标在不同主题下颜色会变。
    *   *解决方案*：使用 **Canny 边缘检测 + 轮廓匹配 (Contour Matching)**。只比对形状骨架，忽略填充色。

## 3. 离线阶段：星群选取算法 (Constellation Selection Algorithm)

该算法运行在“进化层”的后台复盘中，输入是经过“多帧交集”清洗后的**静态幽灵骨架**。

### 3.1 物理分层：安全区 (Safe Zones)
我们首先对骨架中的所有节点进行物理过滤：
*   **Top-Zone (Header)**：$Y \in [0, 15\% \times ScreenHeight]$。通常包含导航结构。
*   **Bottom-Zone (Footer)**：$Y \in [85\% \times ScreenHeight, 100\%]$。通常包含全局 Tab。
*   **Middle-Zone (Content)**：$Y \in [15\%, 85\%]$。仅允许选取 **Auxiliary** 锚点，严禁选取 **Core** 锚点。

### 3.2 评分与排序 (Scoring)
对安全区内的节点 $n$ 计算评分 $Score(n)$：
$$Score(n) = W_{type} \cdot S_{ocr} + W_{unique} \cdot S_{freq} + W_{geo} \cdot S_{area}$$

*   $W_{type}$：文本权重 > 图标权重。
*   $W_{unique}$：全局唯一性。如果页面上有 5 个“更多”，该项得分为 0。
*   $W_{geo}$：几何显著性。面积过小（$<20px$）或过大（$>1/3$ 屏）均扣分。

### 3.3 空间非极大值抑制 (Spatial NMS) & 四象限贪婪
为了防止锚点扎堆（导致抗遮挡能力弱），我们采用改进的 NMS 算法：

1.  **初始化**：将屏幕划分为四个逻辑象限（TL, TR, BL, BR）。
2.  **主核选取 (Primary Core)**：
    *   在 **TL (左上)** 或 **TR (右上)** 区域中，选取得分最高的节点作为 $C_1$。通常是 Page Title 或 Back Icon。
3.  **对角副核选取 (Secondary Core)**：
    *   在 $C_1$ 的**对角线象限**（如 TL 对应 BR）中，选取得分最高的节点作为 $C_2$。通常是 Bottom Tab 的高亮项。
4.  **辅助星群填充 (Auxiliary Filling)**：
    *   在剩余区域中，选择 1~3 个节点 $A_i$。
    *   **约束条件**：$A_i$ 与 $C_1, C_2$ 构成的三角形面积必须大于阈值 $T_{area}$（确保三角剖分的鲁棒性）。

## 4. 在线阶段：Quorum 匹配与容灾机制 (Online Matching)

当 Agent 在端侧运行时，需要在 <100ms 内完成匹配。我们不追求“全等”，而是追求**“法定人数通过 (Quorum Sensing)”**。

### 4.1 匹配流水线
1.  **轻量感知**：
    *   对当前屏幕 Top 15% 和 Bottom 15% 区域进行快速 OCR 和 轮廓提取。
    *   *注：不需要全屏 OCR，节省 70% 算力。*
2.  **候选集映射**：
    *   将感知到的元素集合 $O$ 与经验库中的锚点集合 $M$ 进行特征比对。
    *   生成匹配对集合 $P = \{(o, m) | Sim(o, m) > \theta\}$。

### 4.2 拓扑校验 (Topology Verification)
仅特征匹配是不够的（可能两个页面都有“返回”和“设置”）。必须校验**相对几何关系**。

对于匹配对集合 $P$ 中的任意两点 $i, j$，计算其在当前屏幕的距离 $D_{curr}$ 与经验库中的归一化距离 $D_{exp}$。
$$Ratio = \frac{D_{curr}(i, j)}{D_{exp}(i, j)}$$
*   如果所有点对的 $Ratio$ 方差 $\sigma^2$ 小于阈值（说明是整体均匀拉伸/缩放），则拓扑校验通过。

### 4.3 容灾投票逻辑 (The Voting Logic)
定义一个页面 $Page_A$ 的锚点组为 $\{C_1, C_2, A_1, A_2, A_3\}$（共5个）。

*   **Tier 1: 完美匹配 (Confidence: 1.0)**
    *   命中数量 $\ge 4$，且包含 $C_1, C_2$。
    *   *决策*：直接执行高精度的仿射变换操作。
*   **Tier 2: 核心遮挡模式 (Confidence: 0.8)**
    *   $C_1$ 丢失（如被通知遮挡），但 $C_2$ 命中，且 $A_1, A_2, A_3$ 至少命中 2 个。
    *   *推论*：页面身份确认无疑，但坐标系原点受损。
    *   *决策*：降级为“单点相对定位”，以 $C_2$ 为原点计算动作坐标。
*   **Tier 3: 语义漂移模式 (Confidence: 0.6)**
    *   $C_1, C_2$ 都命中，但所有 $A_i$ 都丢失或特征不匹配。
    *   *推论*：可能是 UI 改版，或者是极其相似的孪生页面。
    *   *决策*：**中断快路径**。唤醒 System 2 (VLM) 进行全屏语义核验，确认无误后触发“进化层”更新锚点数据。

## 5. 关键技术答疑 (FAQ & Edge Cases)

### Q1: 如果页面是可以无限滚动的（Feed流），底部的 Core Anchor 不存在怎么办？
**A:** 对于长列表页，系统会自动检测页面属性。如果判定为 Scrollable，算法会自动切换为 **"Header-Only Constellation"** 模式。
即只选取 Top Zone 的 $C_1, C_2$ 和 Middle Zone 上部的 $A_1$。同时，动作执行将绑定“滑动寻找 (Swipe-to-Find)”逻辑，而不是静态点击。

### Q2: 如何区分“订单详情页”和“退款详情页”？它们结构几乎一样。
**A:** 这正是 **Auxiliary Anchor (辅助锚点)** 的作用。
虽然两者都有返回键、底栏，但“订单详情页”通常会有“去支付/确认收货”等特定文本，而“退款详情页”会有“退款金额/进度”。离线进化层的**“最大熵原则”**会特意挑选这些最具区分度的文本作为辅助锚点，从而在在线匹配时通过 Text Content 区分二者。

### Q3: 为什么不直接用 SIFT/ORB 特征点匹配？
**A:** 传统特征点算法（SIFT/ORB）对旋转和缩放鲁棒，但对**UI 扁平化设计**非常不敏感。现代 UI 包含大量纯色块、圆角矩形，缺乏纹理细节，SIFT 提取的特征点极其稀疏且不稳定。相比之下，基于 OCR 和 轮廓（Shape）的语义锚点更符合人类对 UI 的认知模式。
